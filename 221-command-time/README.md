# Практика 2.2 — Управление ходом исполнения ВПО

Проект `221-command-time` для Raspberry Pi Pico / RP2040, прошивка 1.1.0.
Реализованы задания 2.2.1–2.2.5 из актуальной книги курса.

## Команды

| Команда | Результат |
| --- | --- |
| `clk_info` | Настроенная и измеренная частоты ref/sys/peri/usb/adc, частота ROSC |
| `uptime` | Миллисекунды с запуска по аппаратному таймеру |
| `calc_pi` | Миллион членов ряда Лейбница в double, результат и время расчёта |
| `main_time_exec` | Средняя и максимальная длительность итерации |
| `main_time_reset` | Сброс максимума |
| `clk_sys_low` | Частота ядра 62,5 МГц |
| `clk_sys_default` | Возврат к частоте SDK, 125 МГц |
| `info`, `version`, `ping` | Паспорт, версия и проверка связи |
| `mem_info`, `fw_info`, `dev_info`, `boot_info` | Команды памяти из занятия 2.1 |

Светодиод на GPIO 25 переключается каждые 500 мс. Команды `enable`/`disable`
и опрос кнопки удалены. Приём USB не содержит задержек; сохранены эхо,
обработка CR/LF, Backspace и отказ от выполнения переполненной строки.

`calc_pi` намеренно блокирует суперцикл: ответ на следующую команду будет
после завершения расчёта. Оценка по таблице курса — 4,68 с при 125 МГц и
9,36 с при 62,5 МГц. Это оценка, фактическое время сообщает прошивка на Pico.
Результат записывается в volatile между двумя чтениями часов.

Среднее профилирования хранится в целых числах с дробной частью 1/256 мкс;
N = 2^19. На каждой итерации используются сдвиги, без деления и float.
Разность 32-битных показаний таймера корректна при переполнении.
Восстановление clk_sys не возвращает clk_peri к 125 МГц: стандартная настройка
SDK оставляет периферию на PLL USB с частотой 48 МГц. Объяснение находится в clock.c.

## Сборка в WSL/Linux

```bash
export PICO_SDK_PATH="$HOME/Repositories/pico/pico-sdk"
cmake -S . -B build -DPICO_BOARD=pico
cmake --build build -j4
```

Прошивка: `build/221_command_time.uf2`. Использованы Pico SDK 2.3.0 и ARM GCC 13.2.1.
SDK и результаты сборки не включены в Git.

## Логи без физической платы

`device-2-2-1.log` — `device-2-2-5.log` созданы программной моделью в формате
согласованного примера. В каждом файле явно указано, что плата не использовалась.
USB ID обозначает модель Pico, серийный номер из нулей — заполнитель.
Аппаратные частоты, CHIP_ID, ROSC, GPIO, длительности итераций и обмена
не измерялись на настоящем устройстве. Принят ROSC 5774 кГц, 300 тактов на
обычную итерацию, 585 тактов на член ряда и 40 мкс на вывод строки.

Генератор исполняет настоящие C-алгоритмы `calc_pi` и `profiling` на компьютере
с модельными часами. Перед созданием логов проверяет результат π, рост и спад
среднего, максимум, его сброс и переполнение 32-битного счётчика.
Первое слово таблицы векторов и адрес сброса прочитаны из собственной ARM-сборки.
Сценарии команд берутся из оригинальных `check-2-2-K.py` без изменения скриптов.

Воспроизведение модели после сборки (нужны Python 3 и gcc):

```bash
python3 offline/generate_logs.py
```

Генератор моделирует блокировку суперцикла на `calc_pi`, накопление следующей
команды, возобновление мигания и изменение скорости вычислений при смене частоты.
Это модель, а не эмулятор ARM или подтверждение прогона прошивки на железе.
Принятие формата автоматическими проверками не превращает эти данные в измерения.

При наличии Pico запишите UF2 через BOOTSEL и запустите по очереди
`python check-2-2-1.py` … `python check-2-2-5.py` с установленным pyserial
на системе, где доступен USB COM-порт. Эти скрипты заменят модельные логи
на файлы реального обмена; перед запуском закройте терминал, занимающий порт.
